# 데일리 뉴스레터 운영 메모

매일 아침 브리핑 한 편이 자동으로 발행됩니다. **글쓰기와 발행이 분리돼 있습니다.**

```
루틴 세션            GitHub Issue          GitHub Actions           GitHub Pages
(글만 씀)     ──▶   newsletter: 날짜   ──▶  검증·커밋·배포·이슈 닫기  ──▶  iruki.dev
```

루틴은 저장소를 clone 하지도, 커밋하지도, 빌드하지도 않습니다. 이슈 하나를 여는 것으로 끝납니다.
저장소에 쓰는 주체는 CI 한 곳뿐이라 권한이 모이고, `npm ci`·빌드·git 작업이 세션에서 빠져 토큰도 크게 줄었습니다.

## 구성 요소

| 위치 | 역할 |
|---|---|
| [`.claude/newsletter/PROMPT.md`](PROMPT.md) | **작성 사양서.** 구성·분량·문체·중복 규칙은 이 파일만 고치면 됩니다 |
| [`.github/workflows/newsletter-publish.yml`](../../.github/workflows/newsletter-publish.yml) | 이슈 → 파일 → 커밋 → 배포 |
| [`tools/newsletter_publish.py`](../../tools/newsletter_publish.py) | 이슈 본문 검증·변환, 발행 이력 갱신 |
| `public/newsletter-history.json` | 최근 14일 요약 — **중복 방지의 핵심.** 발행 때마다 자동 갱신 |
| `content/newsletter/YYYY-MM-DD.md` | 발행된 레터 |

## 발행 파이프라인

1. 루틴이 원고를 완성하고 `newsletter: YYYY-MM-DD` 제목으로 이슈를 엽니다. 본문이 곧 파일 내용입니다
2. 워크플로가 **제목 규약 + 작성자가 저장소 소유자인지**를 확인합니다. 공개 저장소라 작성자 검증이 필수입니다
3. `newsletter_publish.py`가 검증합니다 — frontmatter 필수 항목, `pubDate`와 제목 날짜 일치, 본문 11,000자 하한, 같은 날짜 파일 존재 여부
4. `npm run build`로 실제 빌드가 되는지 확인합니다
5. 통과하면 커밋·푸시하고, 이슈에 발행 링크를 댓글로 남기고 닫습니다
6. 실패하면 사유와 로그 링크를 댓글로 남기고 **이슈를 열어 둡니다.** 본문을 고쳐 저장하면(`edited`) 다시 시도합니다

## 루틴 등록

Claude Code web → **Routines** → 새 루틴:

- **Schedule**: `0 21 * * *` (UTC 기준 = 한국 시각 매일 오전 6시 시작)
- **Session**: 매 실행마다 새 세션
- **Prompt**:

```
오늘자 iruki.dev 아침 브리핑을 작성하세요.

https://raw.githubusercontent.com/iruki-dev/iruki-dev.github.io/main/.claude/newsletter/PROMPT.md
를 WebFetch로 읽고, 거기 적힌 순서와 규칙을 그대로 따르세요. 그 문서가 이번 작업의 유일한 기준입니다.

저장소를 clone 하거나 파일을 고치지 마세요. 원고는 GitHub 이슈로만 제출하고 끝냅니다.
```

> 사양서를 저장소에서 읽어오므로 프롬프트를 고칠 때 루틴 설정을 건드릴 필요가 없습니다. `raw.githubusercontent.com` 접근이 막힌 환경이라면 `PROMPT.md` 전문을 루틴 프롬프트에 붙여넣어도 됩니다.

## 환경 요구사항 — 네트워크 egress (필수)

**이 설정이 안 되어 있으면 루틴은 매일 중단 보고만 남깁니다.**

Claude Code web 환경은 아웃바운드 접근을 4단계로 제한합니다 ([문서](https://code.claude.com/docs/en/network-config)).

| 정책 | 사용 가능 |
|---|---|
| 네트워크 차단 | ✗ |
| 패키지 매니저만 (기본값) | ✗ — 뉴스·정부 사이트가 전부 403 |
| 패키지 매니저 + 지정 도메인 | △ — 매체를 일일이 등록해야 함 |
| **모든 도메인** | ○ — 권장 |

> `WebSearch`는 서버 쪽에서 실행되어 egress 정책과 무관하게 동작합니다. **검색이 된다고 환경이 정상인 것은 아닙니다.** 사양서 2장의 프리플라이트가 둘을 구분해 판정합니다.

## 튜닝 가이드

| 증상 | 고칠 곳 |
|---|---|
| 항목이 길어 모바일에서 답답함 | `PROMPT.md` 5장의 글자 수 상한을 낮춤 (현재 항목당 250~350자) |
| 같은 소재가 반복됨 | 6장 점검. 이력이 안 읽히는지도 확인 (`public/newsletter-history.json`) |
| 분량이 모자람 | 4장 구성표의 항목 수를 늘림. **문단을 늘리는 방향으로는 고치지 마세요** |
| 분야가 한쪽으로 쏠림 | 3장 리서치 예산의 분야별 검색 횟수를 조정 |
| 편향된 문장이 보임 | 7장 검증 7번에 실제 문장을 예시로 추가 |
| 코너를 바꾸고 싶음 | 4장 ⑨~⑬ 정의를 수정. 구성표의 분량도 함께 조정 |

## 운영 팁

- **이슈가 열린 채 남아 있다면** 발행 실패입니다. 댓글의 사유를 확인하세요. 대개 frontmatter 문제이거나 날짜 불일치입니다
- **같은 날 두 번 발행되지 않습니다** — 파일이 이미 있으면 스크립트가 중단합니다
- **이력 파일은 손으로 고치지 마세요** — 발행 때마다 기존 레터에서 다시 만들어집니다
- 초반에는 아침에 결과물을 훑고 어색한 부분을 `PROMPT.md`에 반영하는 것을 권합니다. 프롬프트는 한 번에 완성되지 않습니다
