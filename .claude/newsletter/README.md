# 데일리 뉴스레터 운영 메모

매일 아침 브리핑 한 편이 자동으로 발행됩니다. **글쓰기와 발행이 분리돼 있습니다.**

```
루틴 세션            GitHub Issue          GitHub Actions           GitHub Pages
(글만 씀)     ──▶   newsletter: 날짜   ──▶  검증·커밋·배포·이슈 닫기  ──▶  iruki.dev
```

레터는 **중요도순 단일 흐름**입니다. 분야별 섹션 없이 오늘 중요한 것부터 나열하고, 뒤에 트렌드(`흐름과 조짐`)·읽을거리·교양·단어·영어 표현이 붙습니다. 뉴스가 적은 날은 문턱 아래 기사로 채우는 대신 트렌드와 읽을거리를 늘립니다. 상세 규격은 사양서 3~5장에 있습니다.

루틴은 커밋도, 빌드도 하지 않습니다. 이슈 하나를 여는 것으로 끝납니다. 저장소에 쓰는 주체는 CI 한 곳뿐이라 권한이 모입니다.

루틴 세션에는 저장소가 체크아웃돼 있지만 읽는 파일은 둘로 제한합니다 — `.claude/newsletter/PROMPT.md`(작성 사양)와 `public/newsletter-history.json`(중복 방지용 이력). 저장소 구조를 파악할 일이 없는 작업이라 그 외 탐색은 토큰 낭비일 뿐입니다. 사양서 0장의 「범위」가 이 제한을 정의합니다.

## 구성 요소

| 위치 | 역할 |
|---|---|
| [`.claude/newsletter/PROMPT.md`](PROMPT.md) | **작성 사양서.** 구성·분량·문체·중복 규칙은 이 파일만 고치면 됩니다 |
| [`.github/workflows/newsletter-publish.yml`](../../.github/workflows/newsletter-publish.yml) | 이슈 → 파일 → 커밋 → 배포 |
| [`tools/newsletter_publish.py`](../../tools/newsletter_publish.py) | 이슈 본문 검증·변환, 발행 이력 갱신 |
| `public/newsletter-history.json` | 최근 14일의 다룬 소재·단어·교양 주제 — **중복 방지의 핵심.** 발행 때마다 자동 갱신 |
| `content/newsletter/YYYY-MM-DD.md` | 발행된 레터 |

## 발행 파이프라인

1. 루틴이 원고를 완성하고 `newsletter: YYYY-MM-DD` 제목으로 이슈를 엽니다. 본문이 곧 파일 내용입니다
2. 워크플로가 **제목 규약 + 작성자가 저장소 소유자인지**를 확인합니다. 공개 저장소라 작성자 검증이 필수입니다
3. `newsletter_publish.py`가 검증합니다 — frontmatter 필수 항목, `pubDate`와 제목 날짜 일치, 본문 6,000자 하한(형식 오류·잘린 원고를 거르는 최소선), 같은 날짜 파일 존재 여부
4. `npm run build`로 실제 빌드가 되는지 확인합니다
5. 통과하면 커밋·푸시합니다
6. **`deploy.yml`을 명시적으로 깨웁니다** (`gh workflow run deploy.yml`). 기본 `GITHUB_TOKEN`으로 만든 push는 다른 워크플로를 저절로 트리거하지 않는 GitHub Actions의 표준 제약이 있어서, 이 단계가 없으면 콘텐츠는 main에 들어가도 사이트에는 반영되지 않습니다
7. 이슈에 발행 링크를 댓글로 남기고 닫습니다. 배포는 비동기라 링크가 실제로 뜨기까지 몇 분 걸립니다
8. 실패하면 사유와 로그 링크를 댓글로 남기고 **이슈를 열어 둡니다.** 본문을 고쳐 저장하면(`edited`) 다시 시도합니다

> 각 단계가 잘 돌았는지는 [Actions 탭](https://github.com/iruki-dev/iruki-dev.github.io/actions)에서 "Publish newsletter from issue"와 "Deploy to GitHub Pages" 둘 다 확인하세요. 전자만 초록불이고 후자가 그 뒤로 안 돌았다면 배포 트리거가 실패한 것입니다.

## 루틴 등록

Claude Code web → **Routines** → 새 루틴:

- **Schedule**: `0 21 * * *` (UTC 기준 = 한국 시각 매일 오전 6시 시작)
- **Session**: 매 실행마다 새 세션
- **Prompt**:

```
오늘자 iruki.dev 아침 브리핑을 작성하세요.

`.claude/newsletter/PROMPT.md` 파일을 Read로 열어, 거기 적힌 순서와 규칙을 그대로 따르세요.
그 문서가 이번 작업의 유일한 기준입니다. 문서가 지시하는 것 외에는 저장소의 어떤 파일도
열지 마세요 — README, config, content/pages, components 등 전부 포함해서, 그리고 npm이나
git 명령도 실행하지 마세요. 원고는 GitHub 이슈로만 제출하고 끝냅니다.
```

> 사양서는 로컬 파일을 직접 읽습니다(웹으로 fetch하지 않습니다) — 이미 체크아웃돼 있는 파일이라 여는 비용이 거의 없고, 요약을 거치지 않아 규칙이 그대로 전달됩니다. 프롬프트를 고칠 때도 루틴 설정을 건드릴 필요가 없습니다(같은 경로를 다시 읽을 뿐이므로). 이 저장소가 아닌 별도 환경에서 돌리는 등 로컬 체크아웃이 없는 구성이라면 `raw.githubusercontent.com`의 `PROMPT.md`를 `WebFetch`로 대신 읽게 하세요.

## 환경 요구사항 — 네트워크 egress (필수)

**이 설정이 안 되어 있으면 루틴은 매일 중단 보고만 남깁니다.**

Claude Code web 환경은 아웃바운드 접근을 4단계로 제한합니다 ([문서](https://code.claude.com/docs/en/network-config)).

| 정책 | 사용 가능 |
|---|---|
| 네트워크 차단 | ✗ |
| 패키지 매니저만 (기본값) | ✗ — 뉴스·정부 사이트가 전부 403 |
| 패키지 매니저 + 지정 도메인 | △ — 매체를 일일이 등록해야 함 |
| **모든 도메인** | ○ — 권장 |

> `WebSearch`는 서버 쪽에서 실행되어 egress 정책과 무관하게 동작합니다. **검색이 된다고 환경이 정상인 것은 아닙니다.** 사양서 1장 2단계의 프리플라이트가 둘을 구분해 판정합니다.

## 튜닝 가이드

| 증상 | 고칠 곳 |
|---|---|
| 항목이 길어 모바일에서 답답함 | `PROMPT.md` 5장 ③의 순위별 분량표와 6장의 문장·문단 상한 |
| 같은 소재가 반복됨 | 7장 중복 금지. 이력이 안 읽히는지도 확인 (`public/newsletter-history.json`) |
| 중요하지 않은 항목이 실림 | 3장 문턱(뉴스 가치 2개 이상)과 배제 목록을 조임 |
| 분야가 한쪽으로 쏠림 | 3장 배제 목록의 "같은 산업 3건째" 규칙. 분야 할당량은 의도적으로 두지 않았습니다 |
| 편향된 문장이 보임 | 7장 중립성 표의 "쓰면 안 되는 것"에 실제 문장을 추가 |
| 코너를 바꾸고 싶음 | 5장 ④~⑩ 정의를 수정하고 4장 구성표의 분량도 함께 조정 |
| 세션이 다른 파일을 탐색함 | 0장 「범위」가 지켜지는지 실행 로그로 확인 |
| 특정 날짜가 통째로 안 올라옴 | 1장 1·3단계의 날짜 확정·정합성 점검. 한국 시각 이른 아침은 UTC로 전날이라 날짜를 잘못 계산하기 쉬움 — 실제로 2026-09-19자가 이 문제로 빠진 적이 있음 |

## 운영 팁

- **이슈가 열린 채 남아 있다면** 발행 실패입니다. 댓글의 사유를 확인하세요. 대개 frontmatter 문제이거나 날짜 불일치입니다
- **어느 날짜가 아예 안 보인다면** 그날 이슈 자체가 안 만들어진 것입니다 — 발행 실패와 달리 이슈도 댓글도 남지 않아 조용히 지나갑니다. 사양서 3단계의 날짜 정합성 점검이 이런 조용한 결번을 줄이기 위한 장치입니다
- **같은 날 두 번 발행되지 않습니다** — 파일이 이미 있으면 스크립트가 중단합니다
- **이력 파일은 손으로 고치지 마세요** — 발행 때마다 기존 레터에서 다시 만들어집니다
- 초반에는 아침에 결과물을 훑고 어색한 부분을 `PROMPT.md`에 반영하는 것을 권합니다. 프롬프트는 한 번에 완성되지 않습니다
