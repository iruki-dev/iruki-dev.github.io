**콘텐츠를 GUI로 편집하는 블록 기반 정적 사이트.** 페이지·컬렉션·설정을 모두 로컬 admin 도구에서
다루고, 데일리 뉴스레터는 GitHub 이슈에서 CI 파이프라인으로 자동 발행된다.

## 배경

개인 사이트는 고치기 쉬워야 유지된다. 마크다운과 JSON을 직접 편집하는 방식은 결국 업데이트를
미루게 만든다. `content/pages/`를 사이트 구조, `content/<collection>/`을 데이터 리스트로 나누고,
둘 다 같은 GUI에서 편집되도록 설계했다. 하드코딩된 `.astro` 페이지는 없고 `pages/`에는 라우트
디스패처 3개만 둔다.

## 구현

- **블록 빌더** — 20종 블록(콜아웃·갤러리·탭·타임라인·스크롤 카운터·Mermaid·KaTeX·샌드박스
  플레이그라운드 등). `collection-list` 블록 하나가 모든 데이터 리스트 표시를 담당해, 홈 미리보기와
  인덱스 페이지를 같은 코드로 처리한다
- **동적 컬렉션** — 컬렉션 정의가 설정 JSON에 있어 admin에서 추가·이름변경·삭제가 가능하고,
  디렉터리 생성·이동까지 함께 처리된다. 스키마는 zod로 공유
- **로컬 admin 도구** — Node 표준 라이브러리만 쓰는 단일 파일 서버 2,200줄. 외부 의존성·인증·네트워크
  호출 없이 프로젝트 파일을 직접 읽고 쓴다. 저장하면 dev 서버에 즉시 반영되고, 커밋이 곧 콘텐츠 이력
- **테마** — 사이트 전역 팔레트 8종을 CSS 변수로 관리하고, 라이트·다크는 방문자별로 기억한다

## 설계 판단

### 작성과 발행의 권한을 분리

뉴스레터 자동 발행의 초기 구조는 작성 주체가 저장소를 clone하고 커밋하고 빌드했다. 이를 이슈 한
건을 여는 것으로 축소하고, 저장소에 쓰는 주체를 CI 한 곳으로 모았다.

```
작성 → GitHub Issue → Actions(검증·커밋·배포·이슈 종료) → GitHub Pages
```

결과적으로 쓰기 권한 범위가 좁아졌고, 작성 과정에서 `npm ci`·빌드·git 작업이 빠졌다. 중복 주제를
막기 위해 최근 14일 요약 파일을 발행 시점에 자동 갱신한다. 구성·분량·문체 규칙은 별도 사양서
파일 하나에 모아, 발행 로직을 건드리지 않고 편집 방침만 바꿀 수 있게 했다.

## 성과

- **마크다운·JSON을 직접 열지 않고 콘텐츠 전체를 편집 가능** — 항목 CRUD, 페이지 블록 빌더,
  컬렉션 관리, 사이트 설정, 이미지 업로드를 admin 한 곳에서 처리
- **뉴스레터 8호 무인 발행** — 저장소 쓰기 권한을 CI로 단일화하고 작성 단계에서 빌드 의존성을 제거
- **확장 비용 최소화** — 새 컬렉션 추가는 설정 한 줄, 새 페이지 추가는 JSON 파일 하나
